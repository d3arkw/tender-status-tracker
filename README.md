# Tender Status Tracker

Сервис для отслеживания статусов тендеров. Можно создать тендер, переводить его по статусам и смотреть историю изменений — кто, когда и зачем поменял статус.

## Стек

- Python 3.13, FastAPI
- SQLAlchemy 2.0 (async) + asyncpg
- Alembic (миграции)
- PostgreSQL, Redis
- Docker / Docker Compose
- GitHub Actions
- pytest, flake8, black
- uv (зависимости и окружение)

## Структура проекта

```
app/
├── api/routes/      эндпоинты
├── services/        бизнес-логика (переходы статусов, кэш)
├── models/          модели БД
├── schemas/         pydantic-схемы для запросов и ответов
├── database/        движок, сессии
├── core/            конфиг (.env), redis-клиент
└── main.py          точка входа
```

Роутеры только принимают запросы и отдают ответы, вся логика лежит в services.

## Логика решения

### Статусы и переходы

У тендера четыре статуса: `draft` (черновик), `active` (активен), `won` (выигран), `lost` (проигран).

Допустимые переходы описаны в словаре `ALLOWED_TRANSITIONS` в `app/services/tender_service.py`:

- draft → active
- active → won, lost
- won и lost — конечные, из них уже никуда не перейти

Если переход не разрешён, сервис возвращает ошибку, а API отвечает 400.

### Создание тендера

Создаётся запись со статусом draft. Время создания и обновления ставит сама база (`server_default`), поэтому после commit делаю `refresh`, чтобы забрать эти значения и вернуть в ответе.

### Смена статуса (главная часть)

1. Ищу тендер по id. Если нет — 404.
2. Проверяю, можно ли перейти из текущего статуса в новый (по словарю выше).
3. Если можно — в одной транзакции создаю запись в `tender_status_history` (старый статус, новый, кто изменил, причина) и обновляю статус тендера.
4. После commit удаляю кэш тендера из Redis, чтобы следующий GET не отдал старые данные.

Почему всё в одной транзакции: если бы история и статус сохранялись двумя отдельными запросами, при ошибке данные разъехались бы — статус поменялся, а в истории нет записи. А так либо сохранилось всё, либо ничего.

### Чтение с кэшем (cache-aside)

При `GET /tenders/{id}` сначала смотрю в Redis по ключу `tender:{id}`. Если данные есть — отдаю их сразу. Если нет — читаю из базы, кладу в Redis на 300 секунд и отдаю. Так повторные запросы не дёргают базу.

Кэш чистится при каждом изменении статуса, поэтому он не успевает устареть.

### История изменений

Каждое изменение статуса автоматически пишется в `tender_status_history`. Эндпоинт истории отдаёт записи в порядке по времени.

## Эндпоинты

- POST /tenders — создать тендер
- GET /tenders/{id} — получить тендер
- PATCH /tenders/{id}/status — сменить статус
- GET /tenders/{id}/history — история изменений
- GET /health — проверка что сервис работает

Пример смены статуса:

```bash
curl -X PATCH http://localhost:8000/tenders/1/status \
  -H "Content-Type: application/json" \
  -d '{"new_status": "active", "changed_by": "denis", "reason": "начинаем работу"}'
```

Если переход недопустимый, придёт 400 с текстом ошибки, например: `{"detail": "invalid transition from won to lost"}`.

## Запуск

### Локально

Нужны Python 3.13, uv и запущенные PostgreSQL и Redis.

```bash
uv sync
cp .env.example .env
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Swagger-документация будет на http://localhost:8000/docs

### Через Docker Compose

```bash
docker compose up --build
```

Поднимутся три контейнера:

- app — приложение, порт 8000
- db — PostgreSQL 16 (наружу отдаётся на порт 5433, потому что у меня локально 5432 занят своим постгресом)
- redis — Redis 7, порт 6379

При старте приложение само применяет миграции (`alembic upgrade head` в команде запуска) и ждёт готовности базы и redis через healthcheck.

## Тесты

```bash
uv run pytest
```

Покрыл логику переходов, валидацию схем и сервис (тесты на фейковой сессии, реальную базу не поднимаю).

## CI

В GitHub Actions на каждый пуш запускаются black --check, flake8 и pytest. Статус виден на вкладке Actions.
